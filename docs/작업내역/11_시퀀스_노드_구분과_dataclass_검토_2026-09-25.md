# 시퀀스 구조와 데이터 모델 정리

기준: 2026-09-25 현재 `cable_inspection` 실행 코드.

## 실행 경계

| 영역 | 코드 | 책임 |
|---|---|---|
| Main | `sequence/main/node_main.py`, `seq_main.py` | 실행 판단·레시피 선택과 단일 모션 실행권, #00·#01·#07 |
| Inspection | `sequence/inspection/seq_inspection.py`, `sequence/inspection/node_inspection.py` | #03~#05 모션과 #06 비동기 판정 |
| Home Return | `sequence/home_return/seq_home_return.py` | #02 이완·Safe Escape·Access/Home 경로·도달 검증. Main이 상태·실행권을 관리 |
| Recipe | `recipe/recipe.py`, `recipe/node_recipe.py` | 입력 검증·보관·배열 순회·결과/현황 관리. START 외부 서비스는 HMI 통신 노드가 소유 |
| Robot | `robot/m0609.py`, `robot/node_robot.py` | M0609 통신·raw component와 이를 상속한 API 노드 |
| GripperTool | `gripper_tool/rg2.py`, `gripper_tool/node_gripper_tool.py` | 자체 RG2 통신·raw component와 이를 상속한 API 노드 |
| Shared runtime | `sequence/common/motion.py` | Main이 전달한 두 장비 API로 계측·MoveJ/MoveL 완료 확인 |

실행 중인 ROS 노드는 HMI 통신용 `ccc_hmi_node`, Main의 `ccc_sequence_node`, 판정용 `ccc_inspection_node`, 레시피 처리용 `ccc_recipe_node`, 로봇용 `ccc_robot_node`, 그리퍼용 `ccc_gripper_tool_node`과 별도 프로세스의 읽기 전용 `ccc_robot_state`다. Inspection과 Home Return의 모션은 Main의 한 Worker에서 순차 실행한다. HMI 코드와 기존 `/cable_inspection/...` 통신 계약은 변경하지 않았다.

Main 실행 노드는 `InspectionSequence`와 `HomeReturnSequence`를 명시적으로 import해 `MainSequence`에 전달한다. Controller가 HMI Heartbeat와 시스템·검사 레시피 준비 여부를 판단한다. Controller는 #00·#01·#07의 실행 순서와 상태를 관리하고, #02는 상속하지 않고 호출할 때마다 독립 시퀀스 객체로 실행한다. #03~#05도 같은 장비 연결을 받아 Point별로 실행한다. #06 Judgment는 별도 ROS 노드로 유지한다.

## 의존 방향과 수명

Python 모듈의 내부 import 그래프에는 순환이 없다. `JobStopped`는 Main 전용 위치에서 `sequence/__init__.py`로 옮겨 Home Return이 Main의 하위 모듈에 의존하지 않게 했다.

실행 객체는 Main 노드 → Controller → 장비 객체 순서로 소유한다. 반대 방향의 상태 조회·로그·Snapshot·제어 감시 콜백은 약한 참조를 사용하므로 이 소유 고리가 다시 닫히지 않는다. Main 노드가 없어지면 통신 가능 여부는 `False`, Controller가 없어지면 장비 호출은 오류로 종료한다.

## 남긴 dataclass 8개

| 모델 | 남긴 이유 |
|---|---|
| `SequenceResult` | 시퀀스 단계의 성공·실패 반환 계약 |
| `JobContext` | Job과 Pause/Resume 동안 유지되는 상태 |
| `InspectionPointResult` | 포인트의 모션·판정·기록 상태를 한 곳에 저장 |
| `JudgmentRequest` | 비동기 판정 노드로 보내는 입력 계약 |
| `Judgment` | ROS 메시지와 독립적인 순수 판정 결과 |
| `RobotRuntimeConfig` | `sequence/*/data_models/의 개별 정의 파일`의 장비 공통 속도·허용오차·통신 제한값 |
| `RobotPose` | 함께 검증해야 하는 TASK·JOINT 자세 |
| `BoxBoundary` | 시스템 레시피 작업영역의 좌표 검증과 Home 분기 |

## 제거한 dataclass 9개

- `InspectionPoint`, `InspectionRecipe`: 운영 실행에서 사용하지 않던 예전 레시피 모델. 수신 레시피 배열을 그대로 사용한다.
- `PointRuntime`: `InspectionPointResult`와 중복된 포인트 상태. Recipe가 하나의 기록을 관리한다.
- `AdaptiveGripResult`: 검사 단계의 일시적인 중간 결과. 기존 `inspection_results.json`의 `adaptive_grip` 필드와 하위 키는 유지한다.
- `ForbiddenRegion`, `BoundaryCheckResult`, `WorkspaceBoundary`: 현재 실행 경로에서 호출되지 않는 미래용 작업영역 모델. 실제 운영 코드는 `BoxBoundary`로 `work_area`를 검증하고 Home Return 분기에 사용한다. 금지영역·경로 충돌 판정은 현재 구현되어 있지 않다.

`cable_interfaces/msg`와 `srv`는 ROS 통신 계약이며 이 Python dataclass 수에 포함하지 않는다. 결과 JSON과 HMI 서비스·토픽 필드는 유지했다. 이후 새 데이터 모델은 실제 소유 상태나 통신 경계가 생길 때만 추가한다.

## 레시피 책임 분리 후 보완

Recipe component는 ROS를 import하지 않고, 메시지 변환은 Recipe 노드에 둔다. 두 입력 경로 모두 동일한 전체 검증을 적용한다. 원본 편집·저장 API는 제거했다. Main은 시스템 설정을 사용하고 검사 배열과 순회 상태는 Recipe가 소유한다. Home Return은 시스템 복사본을 인자로 받고, 장비 런타임은 레시피 파일이나 객체를 보관하지 않는다. 자세 오차·탈출 방향 계산은 `sequence/common/geometry.py`로 옮겼다. 외부 통신 계약은 유지하며 Recipe 노드는 같은 프로세스에서 API로 연결한다.

## Robot·GripperTool 책임 분리 후 보완

`HardwareContext`와 `hardware/` 중계 구조를 제거했다. `SequenceMotion`은 장비를 상속하지 않고 Robot·GripperTool 노드를 받아 사용한다. 장비들은 서로의 통신·메타데이터·노드를 참조하지 않는다. 그리퍼는 자체 서비스 제공자 확인으로 real/virtual 연결을 검증한다. Main Worker가 두 장비를 순차 호출하고, 종료 시 Worker를 끝낸 뒤 각 노드를 해제한다. 장비별 준비 API의 호출 순서는 Sequence가 소유한다.

레시피의 독립 검증 함수는 제거했다. `RobotPose.validate()`는 자세, `Recipe.validate()`는 포인트 조건과 전체 계약을 검증한다. 시스템 설정 읽기·검증은 `Recipe.system_recipe()`가 담당한다. ROS 메시지 변환은 `RecipeNode.decode_message()`와 `encode_message()`에서 직접 처리하며 외부 보조 함수로 중계하지 않는다.

## Recipe 순회와 HMI 현황

`OperatingInspectionPoint`와 `OperatingInspectionRecipe`를 제거했다. Recipe는 수신 points 배열을 실행 시작 시 고정하고 `next_point()`로 활성 포인트를 순서대로 제공한다. 완료 전 재요청은 같은 포인트를 반환한다. Main은 검사 실행과 `complete_point()` 결과 반영을 담당하고 Inspection은 `run_point()`로 한 포인트만 검사한다.

현재 포인트·완료 수·판정 대기·결과는 Recipe가 관리한다. JobContext에는 작업 ID·운전 상태·재개 정보만 남겼다. Main은 Recipe 진행 현황을 기존 work_status 필드로 발행하고 judgment_result 경로를 유지한다. 종료 후 마지막 현황을 유지하고 이전 run_id 판정은 다음 실행에 반영하지 않는다.

실행 스냅샷 points도 수신 메시지와 같은 배열이다. 구형 파일의 points 객체와 execution_order는 입력 경계에서만 변환한다. HMI 코드와 msg/srv 정의는 변경하지 않았다.

## 시퀀스 component와 실행 노드 정리

Main·Inspection·Home Return·Common 기능별 폴더에 시퀀스와 관련 노드를 함께 배치한다. 파일명은 seq_main.py, node_main.py, seq_inspection.py, node_inspection.py, seq_home_return.py로 기능을 명시한다.

Main은 ROS나 판정 노드를 import하지 않고 Inspection의 준비·실행·결과 API를 사용한다. 판정 연결은 Job 간 재사용하고 STOP/종료 시 Worker가 끝난 다음 해제한다. Inspection의 단순 명령 중계 7개와 판정 통신의 미사용 대기 메서드 2개를 제거했다. 단계별 정책과 체크포인트는 유지한다. 역할 주석은 한 줄로 정리하고 방향·미도달·busy 처리 이유는 해당 코드에 남겼다.

검증: 오프라인 198개, 기존 격리 ROS 통합 4개 통과(시퀀스 파일 배치 정리 시점). cable_inspection 빌드 성공. 내부 Python 모듈 26개의 import 그래프에 순환 없음. 실물 모션은 실행하지 않았다.

## 검사·판정 책임 이동

Inspection이 판정 목록 초기화, 준비 대기, 요청, 오류 결과 생성과 결과 조회를 담당한다. Main은 다음 포인트 검사 지시와 Recipe 결과 반영·작업 로그를 담당한다. 판정 노드는 내부 직접 호출 API를 제공하며 Inspection에 전달한다. JudgmentClient와 내부 ROS 왕복은 제거했다. 판정 Worker와 모션 Worker의 결과 공유는 잠금과 복사본으로 보호한다. 전체 레시피를 Inspection에 저장하지 않고 식별 정보만 전달한다.

장비 준비·공통 모션 책임 재배치는 아래 후속 작업에서 완료했다. HMI 통신 분리도 아래 후속 작업에서 완료했다. HMI 화면 코드와 기존 통신 필드는 변경하지 않았다.

검사·판정 책임 이동 검증: 오프라인 198개, 격리 ROS 통합 5개 통과. Robot ROS 객체 없이 Inspection 요청·결과 수신 확인. 패키지 빌드 성공, 내부 import 순환 없음.

## 데이터 파일 분리

기존 models.py를 제거하고 dataclass마다 별도 파일로 분리했다. Main 전용 JobContext는 main/data_models, 검사 전용 InspectionPointResult·JudgmentRequest·Judgment는 inspection/data_models, 공통 SequenceResult·RobotRuntimeConfig는 common/data_models에 둔다. Enum과 파지 예외도 해당 기능에 독립 파일로 배치한다. __init__.py에서 재수출하지 않고 정의 파일을 직접 import한다. RobotPose와 BoxBoundary는 이번 models.py 분리 대상이 아니며 기존 Recipe·Safety 위치를 유지한다.

## 판정 소유권 최종 정리

InspectionJudgmentNode 하나가 요청 Queue, 판정 Worker, 현재 실행의 결과, 외부 결과 발행을 소유한다. InspectionSequence는 직접 API를 호출한다. 별도 judgment.py는 제거하고 판정 규칙은 InspectionJudgmentNode.judge_request 정적 메서드로 합쳤다. 데이터 구조체 data_models/judgment.py는 유지한다. 실행 진입점이 판정 노드를 한 번 생성·종료하며 Inspection은 주입받은 노드를 종료하지 않는다. 이전 실행의 처리 중 판정과 오류 확정 뒤의 정상 판정은 결과 저장·발행에서 제외한다.


## 장비 준비·공통 모션 책임 재배치

| 기존 common/motion.py 책임 | 현재 소유 위치 |

| prepare / check_robot_operability 준비 순서 | MainSequence.check_devices |
| connected 초기화 여부 | RobotNode / GripperToolNode 각각의 initialized |
| Robot 상태·모드·Tool/TCP·관절 유효성 확인 | RobotNode.check_ready / check_operability |

| Entry/Pull 힘·거리·시간 종료 조건 | InspectionSequence.monitor_contact |
| 축 방향 힘·실제 이동량·피크·최소 폭 | InspectionSequence.measure |

공통 모션에는 일반 이동 도달 확인·상대 목표 계산·정지 대기·Open 폭 확인·원시 계측만 남겼다. 검사 방향과 측정 상태는 Inspection에 한 번만 보관하며 예외에도 접촉 측정 구간을 닫는다. RobotRuntimeConfig에서 레시피와 중복되던 Entry/Pull 힘·시간 4개 필드를 제거했다. 새 클래스와 dataclass는 추가하지 않았다.

동작 정책은 유지했다. busy는 기록용이며 진행 제한 조건으로 쓰지 않는다. 감속 중 피크와 최소 폭을 포함하고, 접촉 미도달은 결과로 기록하며, Hard Grip 완료 실패는 기존 해제·복귀 절차를 거친다. Open/일반 복귀 실패는 성공으로 처리하지 않는다. 포인트별 속도가 공통 설정을 덮어쓰던 부분은 제거하여 Home에는 공통 속도가 적용된다.

기존/새 코드에 동일한 가상 입력을 넣은 6가지 사례(힘 제한·미도달·거리 도달·시간 초과·폭 안정화·파지 실패 복구)에서 명령 순서, 접촉 측정값, 판정 요청이 일치했다. 기존 테스트 항목을 보존하고 호출 대상을 새 책임 위치로 옮겼으며, 실제 검사 코드를 실행하는 가상 피드백 검증을 추가했다. 최종 검증: 오프라인 209개, 격리 ROS 통합 5개 통과, cable_inspection 빌드 성공. HMI 소스와 ROS msg/srv는 변경하지 않았으며 실물 모션은 실행하지 않았다.


## HMI 통신 전담 노드 반영

합의한 `hmi/interface.py`와 `hmi/node_hmi.py`를 추가했다. `HmiNode`가 통신 component를 상속하여 기존 외부 요청·응답 경로를 생성한다. Main 실행 노드는 객체 구성과 Worker를 관리하며 HMI 노드를 기존 실행 진입점에서 함께 생성한다.

- Main에서 이동: StartInspection 서비스, 명령·Heartbeat 구독, 상태·로그·Snapshot 발행, request_id 중복 처리.
- 판정 노드에서 이동: judgment_request 구독과 judgment_result/log 발행. 판정 Queue·결과 저장·계산은 판정 노드에 유지.
- 상태 수집: Robot·GripperTool 노드가 장비별 비동기 상태를 관리하고 HMI 노드가 기존 robot_status로 발행. 별도 상태 노드와 내부 중계 토픽은 제거.
- Main에 유지: 실행 가능 여부, 레시피 선택, 단일 Worker 시작·종료, 명령별 시퀀스 제어.

외부 토픽·서비스 타입·QoS·메시지 필드는 유지했다. HMI 화면 소스와 msg/srv는 변경하지 않았다. 함수 이름은 역할을 명시하고 `def` 위에 기능·인자·반환 설명, 인자 들여쓰기와 메서드 간 3~4줄 간격을 적용했다.

검증: 오프라인 209개와 격리 ROS 통합 7개 통과. 외부 HMI 서비스·발행·구독이 ccc_hmi_node에 모였음을 ROS 그래프로 확인했다. HMI·terminal 요청, 중복 START, 상태·Snapshot·판정 결과 전달, Heartbeat 유실 후 자동 재개 방지도 확인했다. 실물 동작은 수행하지 않았다.


## START 위치 조건 사용자 수정 반영

START 전 Home 경유와 STOP 후 별도 Home 강제를 제거했다. MainSequence.prepare_work_access가 현재 위치별 준비를 담당하며 HomeReturnSequence.escape_work_area를 재사용한다. 이미 Access에 도달했으면 이동을 생략하고, 작업영역 안이면 Open·Tool 역방향 후퇴 후 Access, Home 등 영역 밖이면 Access로 이동한다. Access 확인 전 포인트 검사는 실행하지 않는다. Main 시퀀스, terminal 명령, HMI START 서비스 모두 정리된 SYSTEM_READY/STOPPED/ERROR에서 새 Job을 허용하며 실행·일시정지·정리 중 재진입은 거절한다. 검사 종료 후 자동 Home은 제거하고 Work Access에서 대기한다.

### 검사 완료 후 대기 위치 변경

검사 완료 후 자동 Home Return을 제거했다. 마지막 포인트 검사 후 Work Access로 복귀하고, 판정·기록 완료를 확인하여 SYSTEM_READY로 전환한다. 다음 START는 현재 Access 도달 확인 후 검사를 시작한다. Home은 별도 HOME_RETURN/MOVE_HOME 명령으로만 실행한다.
