# 03. HMI → 로봇 제어·검사 인터페이스 구현 가이드

- 작성: 2026-09-23
- 갱신: 2026-09-25. 인터페이스 타입은 현재 `cable_interfaces`, 동작은 `cable_inspection` 소스를 기준으로 확인한다.
- 대상: HMI 구현 담당자
- 이 문서는 현재 검사 측 구현 계약과 HMI 구현 권고를 구분한다. 문서 작성 과정에서 HMI/검사 코드는 변경하지 않았다.

## 1. 담당 범위와 핵심 변경

| 담당 | 구현 범위 |
|---|---|
| 검사 측 `cable_inspection` | 전체 실행 레시피 수신·검증, 실행 복사본 고정, 로봇/RG2 제어, 판정, 상태·결과 발행 |
| HMI 측 | 화면, 원본 레시피 목록·편집·버전 저장, 시작 서비스 호출, 결과 DB 저장·조회 |
| 공통 `cable_interfaces` | 두 PC에서 같은 버전으로 빌드할 msg/srv 정의 |

**HMI의 기존 `command: START`는 사용하지 않는다.** `/cable_inspection/start` 서비스로 레시피 전체를 보낸다. 검사 측은 HMI 원본 DB를 읽거나 수정하지 않는다. HMI에서 레시피를 선택하는 것만으로 검사 측 레시피가 적용되지는 않는다.

현재 검사 패키지에는 `recipe_manager`, 레시피 목록·조회·저장 서비스, 결과 이력 조회 서비스가 없다. `ListRecipes/GetRecipe/SaveRecipe/QueryResults`는 공통 패키지에 **타입 정의만** 있다. HMI 측에서 이를 사용할 경우 서버·경로·DB 정책을 자체 구현한다. 과거 문서의 `cable_management` 실행 지침을 현재 검사 측 제공 기능으로 해석하지 않는다.

## 2. 통신 구성

아래 경로는 기본 namespace 기준이다. 두 PC의 ROS_DOMAIN_ID, DDS discovery 설정, 메시지 버전이 일치해야 한다. HMI는 `cable_interfaces`를 사용하고 검사 측 Python 내부 모듈을 import하지 않는다.

| 경로 | 형식 | 방향 | QoS/동작 |
|---|---|---|---|
| `/cable_inspection/start` | `cable_interfaces/srv/StartInspection` | HMI → 검사 | 비동기 서비스 호출 |
| `/cable_inspection/command` | `std_msgs/msg/String` JSON | HMI → 검사 | RELIABLE, VOLATILE, depth 50 |
| `/cable_inspection/hmi_heartbeat` | `std_msgs/msg/Empty` | HMI → 검사 | RELIABLE, VOLATILE, depth 10 |
| `/cable_inspection/work_status` | String JSON | 검사 → HMI | RELIABLE, TRANSIENT_LOCAL, depth 1 |
| `/cable_inspection/robot_status` | String JSON | 검사 → HMI | RELIABLE, VOLATILE, depth 10 |
| `/cable_inspection/execution_snapshot` | String JSON | 검사 → HMI | RELIABLE, TRANSIENT_LOCAL, depth 10 |
| `/cable_inspection/judgment_result` | `cable_interfaces/msg/InspectionResult` | 검사 → HMI | RELIABLE, VOLATILE, depth 50 |
| `/cable_inspection/log` | String JSON | 검사 → HMI | RELIABLE, VOLATILE, depth 50 |

`work_status`와 `execution_snapshot` 구독자에도 TRANSIENT_LOCAL을 지정해야 늦게 접속했을 때 보존 데이터를 받는다. snapshot은 최근 최대 10개이며 영구 이력 저장소가 아니다. 결과 토픽에는 과거 결과 자동 재전송 기능이 없다.

검사 PC 실행:

```bash
source /opt/ros/jazzy/setup.bash
source ~/ws_cobot_pjt/ws_dsr/install/local_setup.bash
source install/local_setup.bash
ros2 launch cable_inspection inspection.launch.py control_mode:=hmi
```

로봇/RG2 드라이버는 별도로 실행한다. `robot_mode:=virtual`도 가상 드라이버가 필요한 모드이며 단순 mock이 아니다. HMI 쪽 mock/기존 모니터의 상태 발행을 실제 검사 상태와 혼용하지 않는다.

## 3. HMI 시작 처리 순서

1. ROS 수신 처리를 UI 스레드와 분리하고 상태·결과·snapshot 구독을 먼저 연결한다.
2. heartbeat를 주기적으로 발행한다. **권고: 2 Hz**. 검사 측 만료시간은 시스템 레시피 `heartbeat_timeout_s`로 정해지므로 실제 설정을 확인한다(Main 생성자 기본값 2초).
3. HMI 관리 기능에서 선택한 레시피의 **확정 버전 전체**를 읽어 요청 복사본으로 고정한다.
4. 최근 Main 응답, 서비스 준비, `control_mode == "hmi"`, `run_state in {"SYSTEM_READY", "STOPPED", "ERROR"}`, `work_active == false`를 확인한다. 이것은 화면의 사전 확인이며 최종 접수 판단은 서비스 응답이다.
5. 새 실행에 UUID 등 새 `request_id`를 생성하고 `call_async()`로 한 번 요청한다. 요청 중 중복 클릭을 막는다.
6. `accepted=true`면 접수 상태로 표시하고 `request_id/run_id`를 저장한다. 장비 초기화와 검사 성공을 의미하지 않는다.
7. 실제 진행은 `work_status`, 실행 조건은 `execution_snapshot`, 포인트 판정은 `judgment_result`로 갱신한다. 초기화 실패도 상태·로그로 처리한다.

**응답 대기 권고: 5초, 자동 재전송 없음.** 제한시간 경과는 서버 거절이나 취소를 뜻하지 않는다. 화면에는 “접수 여부 확인 중”을 표시하고 같은 request_id의 상태/snapshot을 확인한다. 통신 timeout에서 새 ID로 다시 실행하지 않는다. 수동 재확인이 필요할 때 같은 ID·같은 레시피를 사용하면 현재 Main 프로세스에서는 중복 실행을 방지한다. Main 재시작 뒤에는 이 보장이 사라지므로 자동 복구 실행하지 않는다.

서비스 응답·snapshot·상태의 도착 순서는 보장하지 않는다. 먼저 도착한 데이터를 ID로 보관한 뒤 연결한다. 취소한 로컬 future도 이미 접수된 로봇 작업을 취소하지 않는다.

### StartInspection 요청·응답

```text
# request
string request_id
InspectionRecipe recipe
---
# response
bool accepted
string code
string message
int64 run_id
```

request_id는 공백만으로 구성할 수 없는 1~128자 문자열이다. 자동 trim하지 않으므로 재확인에는 원문을 유지한다. 새 실행은 새 ID를 사용한다. 거절 응답의 run_id는 0이다.

| code | accepted | HMI 처리 |
|---|---|---|
| ACCEPTED | true | 새 요청 접수, 상태 수신 대기 |
| ALREADY_ACCEPTED | true | 최초 run_id에 연결, 재실행 없음 |
| INVALID_REQUEST_ID | false | ID 형식 수정 |
| INVALID_RECIPE | false | message의 레시피 오류 표시 |
| REQUEST_ID_CONFLICT | false | 같은 ID에 다른 레시피 사용 금지; 기존 요청 확인 |
| CONTROL_MODE_MISMATCH | false | terminal 모드 안내, HMI 운전 비활성 |
| HEARTBEAT_MISSING | false | heartbeat 송신·통신 확인 |
| BUSY | false | Worker 또는 작업 context 정리 대기 |
| NOT_READY | false | 실행·일시정지 상태인지 확인. STOPPED/ERROR는 작업 정리 후 새 START 허용 |
| NO_ENABLED_POINTS | false | 활성 포인트 선택 |

검증 순서는 ID → 레시피 → 중복 요청 → 제어 모드 → heartbeat → BUSY → 준비 상태 → 활성 포인트다. `message`는 상세 설명용이며 분기 처리는 `code`를 사용한다.

## 4. 전송할 레시피

### InspectionRecipe

| 필드 | 타입 | 규칙 |
|---|---|---|
| recipe_id | string | 공백뿐인 값 금지, 1~256자 |
| recipe_version | string | 공백뿐인 값 금지, 1~256자; 전송 시 명시 |
| coordinate_frame | string | `BASE`만 지원 |
| connector_type | string | 공백뿐인 값 금지, 1~256자 |
| points | InspectionPoint[] | 1~1000개, **배열 순서가 실행 순서** |

### InspectionPoint

| 필드 | 타입 | 규칙 |
|---|---|---|
| point_id | string | 공백뿐인 값 금지, 최대 256자, 레시피 내 중복 금지 |
| point_name | string | 최대 256자; 현 검증은 빈 이름을 허용하나 화면용 이름 입력 권고 |
| enabled | bool | false인 포인트는 실행에서 제외; 시작에는 최소 하나 true 필요 |
| ready_pose | InspectionPose | task와 joint 모두 필요 |
| entry_pose | InspectionPose | task와 joint 모두 필요 |
| entry_setting | EntrySetting | 아래 조건 전체 필요 |
| grip_setting | GripSetting | 아래 조건 전체 필요 |
| pull_setting | PullSetting | 아래 조건 전체 필요 |

`InspectionPose.task`는 고정 길이 float64[6], `[X,Y,Z,A,B,C]`이며 BASE mm·deg, 자세는 ZYZ다. `joint`는 float64[6], J1~J6 deg다. 모두 유한한 수여야 한다. task/joint는 같은 자세를 교시한 한 쌍으로 제공한다. joint만 보내는 방식과 누락 좌표를 0으로 채우는 방식은 사용하지 않는다. 현 형식 검증에서 0 좌표 통과가 실제 작업 위치의 적합성을 뜻하지는 않는다.

Ready pose → Entry pose는 MoveJ **접근(approach)**이며 목표 확인 시간 초과 시 미도달을 기록하고 후속 단계로 진행한다. Entry pose에서 Soft Grip과 함께 Entry task의 자세각으로 계산한 Tool +Z 방향으로 이동하는 구간이 **진입(entry)**이다. Pull은 그 반대 방향이다. 지정 거리는 접촉 이동의 상한이며 저항으로 미도달해도 실제 힘·이동량으로 판정한다. 직선 복귀에도 Entry task가 사용된다. 별도 `entry_direction` 필드는 전송하지 않는다.

| 하위 타입 | 필드 | 단위/조건 |
|---|---|---|
| EntrySetting | max_distance_mm | mm, 0 초과 25 이하 |
| | force_guard_n | N, 양수 |
| | timeout_s | s, 양수 |
| GripSetting | soft_close_width_mm, soft_open_width_mm, hard_width_mm | mm, 각각 양수 |
| | soft_force_n, hard_force_n | N, 각각 양수 |
| PullSetting | force_limit_n | N, 기준 Pull 힘/정지 요청 기준 |
| | max_distance_mm | mm, 최대 Pull 이동거리 |
| | timeout_s | s |
| | speed_mm_s | mm/s |
| | normal_displacement_limit_mm | mm, 합격 허용 변위 |

Entry 최대거리는 25 mm 이하이다. Pull 거리 및 Entry/Pull timeout에는 별도 고정 상한을 적용하지 않는다. 모든 setting 값은 유한한 양수여야 하며 **비활성 포인트도 전체 구조 검증 대상**이다. ROS 숫자 기본값 0을 그대로 보내면 거절된다. 힘 정지 기준과 변위 합격 기준은 별개다. 실제 최대 힘은 감속 정지 중 기준을 초과할 수 있으므로 설정 힘을 최대 실측 힘으로 표시하지 않는다.

현재 msg에는 `cable_id`, `product_id`, 반복 횟수 필드가 없다. point_id는 검사 위치 식별자다. HMI 자체 관리 필드를 전송 계약에 임의로 추가하지 않는다. Home·작업영역·Tool/TCP 등 시스템 레시피는 검사 측 소유다.

### 메시지 생성 예시

아래 `saved`는 HMI가 읽은 확정 버전 dict이며, `points`는 실행 순서의 배열이다. 실제 좌표·조건은 저장된 교시값으로 채운다. Qt 화면 갱신은 ROS callback에서 직접 하지 말고 signal/queue로 전달한다.

```python
import copy
import uuid
from cable_interfaces.msg import InspectionRecipe
from cable_interfaces.srv import StartInspection
from rosidl_runtime_py.set_message import set_message_fields

recipe = InspectionRecipe()
set_message_fields(recipe, copy.deepcopy(saved))
request = StartInspection.Request(
    request_id=str(uuid.uuid4()), recipe=recipe)
client = node.create_client(StartInspection, '/cable_inspection/start')
if client.service_is_ready():
    future = client.call_async(request)
    # request를 응답/timeout 처리 종료까지 보존한다.
    # 완료 callback에서 accepted/code/message/run_id를 UI로 전달한다.
```

내부 저장 형식이 `points: {point_id: ...}`와 `execution_order`라면 ROS 메시지 생성 전에 다음과 같이 변환한다. 임의의 키 정렬로 순서를 바꾸지 않는다.

```python
wire = copy.deepcopy(saved_snapshot)
wire['points'] = [wire['points'][pid]
                  for pid in wire.pop('execution_order')]
```

## 5. 상태 수신과 화면 처리

### work_status — Main 생존 및 작업 상태

작업 중 10 Hz, 대기 중에는 변경 시 또는 SYNC 요청 시 발행한다. **대기 중 주기 발행이 없다는 이유만으로 연결 끊김으로 판단하지 않는다.** HMI 권고는 1초마다 SYNC 전송, 마지막 work_status 수신 후 3초 무응답이면 Main 통신 끊김 표시다. 로컬 단조 시각으로 수신 시간을 관리한다. TRANSIENT_LOCAL의 과거 상태 한 건만으로 현재 Main 생존을 확정하지 않는다.

| 필드 | 의미/표시 기준 |
|---|---|
| schema_version, stamp | 현재 schema_version=1, 발행 시각 |
| run_state | SYSTEM_READY / RUNNING / PAUSE_REQUEST / PAUSED / STOPPED / ERROR |
| state | SYSTEM_READY만 IDLE로 변환한 호환 표시값; 나머지는 run_state와 같음 |
| operation | 초기 빈 문자열 / INSPECTION / HOME; 종료 뒤에도 마지막 값 유지 |
| work_active | 현재 작업 진행 여부; operation만으로 실행 여부 판단 금지 |
| request_id, run_id | 요청·실행 연계 키 |
| control_mode, control_connected | hmi 또는 terminal, 선택한 운전 입력 heartbeat 유효 여부 |
| alarm | 오류 설명 |
| recipe_id, selected_recipe_id, recipe_version | 실행/선택 정보; context 없을 때 version이 빈 값일 수 있음 |
| available_recipes | 검사 backend에 알려진 목록; **HMI 원본 레시피 카탈로그가 아님** |
| job_id, execution_index, resume_point | 작업 식별·진행·재개 위치 |
| total_points, current_point, current_step | 활성 포인트 수와 현재 단계 |
| progress_percent, pending_judgments, job_summary | 진행률·판정 대기 수·작업 요약 |
| criteria | 현재 포인트 기준; 없으면 빈 객체 |
| measurement | 현재 포인트 측정; 없으면 null |

criteria 키: `required_pull_force_n`, `max_displacement_mm`, `pull_max_distance_mm`, `grip_width_mm`.

measurement 키: `sample_stamp`, `age_s`, `valid`, `phase`, `measurement_kind`, `pull_force_n`, `pull_displacement_mm`. 현재 구현은 샘플 나이 2초 이하일 때 valid=true다. null/valid=false/수신 만료는 `—`로 표시한다. `robot_status.force_norm_n`을 Pull 축 힘으로 대신 표시하지 않는다.

검사 종료 뒤 request_id는 유지된다. 수동 HOME에서는 request_id가 비워지고 operation=HOME이 된다. HOME의 run_id/recipe 정보에는 이전 검사 값이 남을 수 있어 새 검사로 생성하지 않는다. progress_percent=100만으로 모든 판정 완료를 단정하지 말고 작업 상태·판정 대기·결과를 함께 확인한다.

### robot_status — 독립 장비 상태

기본 발행 주기는 약 0.1초, 장비 조회는 기본 0.2초(Tool/TCP 최소 1초)다. Main 생존과 별도로 표시한다.

- 식별: `schema_version`, `stamp`
- 연결: `robot_connected`, `gripper_connected`
- 좌표: `task`, `joint`
- 측정: `wrench_base`(힘/토크 6축), `force_norm_n`(힘 3축 합력), `gripper_width_mm`
- 상태: `robot_state_code`, `motion_status`, `robot_motion`, `servo`, `servo_source`
- Tool/TCP: `tool.name`, `tool.tcp`
- 품질: `validity`, `age_s`, `errors` — 채널별 객체. tool 이름의 품질 키는 `tool_name`, TCP는 `tcp_name`이다.

실패·만료된 값은 null이다. HMI 자체 수신 시간도 확인하고 권고 2초 이상 수신이 없으면 장비 표시를 만료시킨다. servo는 `servo_source=robot_state_inference`인 추정 상태로, 직접 읽은 신호가 아니다. 로봇 상태만 수신된다고 검사 Main 통신 정상으로 표시하지 않는다.

### execution_snapshot

최상위 키는 `run_id`, `request_id`, `recipe_id`, `recipe_version`, `recipe`다. recipe에는 `recipe_id`, `recipe_version`, `coordinate_frame`, `connector_type`, `execution_order`, `points`가 있다.

**snapshot의 points는 point_id를 키로 한 객체이고 ROS 메시지 points는 배열이다.** 각 point 내용은 InspectionPoint와 같다. 검사 중 원본을 편집하더라도 실행 조건 표시는 snapshot을 유지한다. snapshot 수신 역시 접수 증거이며 실행 성공을 뜻하지 않는다.

## 6. 운전 명령

`command`의 `String.data` 형식:

```json
{"name":"SYNC","args":{}}
```

| name | 동작/상태 조건 |
|---|---|
| SYNC | work_status 즉시 재발행; 과거 결과·snapshot 재전송 명령 아님 |
| PAUSE | RUNNING/PAUSE_REQUEST에서 요청; 원자 동작 완료점에서 정지하므로 PAUSED 수신 전까지 대기 표시 |
| RESUME | PAUSED이며 통신 복구·heartbeat 정상일 때 재개 |
| STOP | 작업 정지 요청; 자동 Home 없음; 정지 완료는 후속 상태로 확인 |
| MOVE_HOME 또는 HOME_RETURN | 별도 Home 복귀; SYSTEM_READY/STOPPED/ERROR 및 작업 정리 상태에서 요청 |

명령 args는 위 명령에서 빈 객체로 충분하다. 응답 서비스는 없으므로 후속 work_status/log로 결과를 표시한다. 클릭 즉시 로컬 상태를 RUNNING/PAUSED 등으로 확정하지 않는다. STOP 뒤 바로 START하지 말고 상태 확인 및 필요한 HOME 복귀를 거친다.

HMI 모드의 START 토픽 명령은 거절된다. SELECT_RECIPE는 검사 backend에 이미 등록된 ID만 선택하는 기존 기능으로 HMI 카탈로그 연동 수단이 아니다. `ESTOP`, `ESTOP_RESET`, `MOVE_TO_POINT`, `SET_SPEED`는 현재 Main에서 지원하지 않는다. STOP 버튼은 작업 정지이며 물리 비상정지 해제 기능으로 표현하지 않는다.

terminal 모드에서는 Main이 `terminal_command/terminal_heartbeat`를 사용하므로 HMI 운전 버튼을 비활성화한다. heartbeat 유실 시 실행 중 Safe Pause를 요청하고, 통신이 복구되어도 자동 재개하지 않는다. 최종 상태를 확인한 뒤 명시적으로 RESUME한다.

## 7. 검사 결과와 로그

`judgment_result`는 포인트별 결과이며 HMI가 수신하여 DB에 저장한다. 표시 기준은 다음과 같다.

| 필드 묶음 | 내용 |
|---|---|
| run_id, stamp, recipe_id, recipe_version, point_id, point_name, cable_type | 실행·포인트·조건 식별 |
| result | PASS / FAIL / SYSTEM_ERROR |
| reason_code, reason, termination_reason | 판정 사유 코드·설명·Pull 종료 사유 |
| judgment_status | PENDING / COMPLETED / ERROR 정의; 최종 판정은 COMPLETED 또는 ERROR |
| sequence_status | IDLE / RUNNING / SUCCESS / FAIL / INCOMPLETE 정의 |
| max_force_n, required_pull_force_n | 최대 실측 힘과 해당 검사 기준 힘(N) |
| displacement_mm, displacement_limit_mm | 실측 변위와 해당 검사 허용 변위(mm) |
| force_data_id, task, joint | 측정 원본 식별자와 Entry 좌표 |
| soft_width_mm, pull_width_mm | Soft 종료 기준 폭, Pull 전체 구간 최소 폭(mm) |
| width_delta_mm, grip_failure_width_mm | Pull 최소 폭−Soft 기준 폭, 파지 실패 판정 폭(mm) |
| db_saved | 메시지 필드; HMI DB 저장 성공은 HMI가 실제 저장 결과로 확인 |

현재 사유 코드: `PASS_FORCE_DISPLACEMENT_OK`, `FAIL_DISPLACEMENT_LIMIT`, `FAIL_MAX_DISTANCE`, `FAIL_GRIP_WIDTH`, `SYSTEM_ERROR`. 이후 알 수 없는 코드는 원문과 reason을 표시한다. SYSTEM_ERROR는 제품 불량과 분리한 판정 미완료로 집계한다. 이전 HMI의 MISSING 분류로 자동 변환하지 않는다.

결과 저장 시 `run_id + point_id`를 현재 실행의 중복 수신 처리 기준으로 사용할 수 있다. 오류 결과에 누락 식별자가 있으면 일반 제품 결과와 분리해 기록한다. 결과 표시에는 원본 레시피를 나중에 다시 읽은 값이 아닌 **결과 메시지에 실린 판정 당시 기준**을 사용한다. 기존 VOLATILE 토픽이므로 재접속 동안 유실된 이력을 SYNC로 복구할 수 없다. HMI 측 상시 저장 및 조회 정책이 필요하다. UI 저장 확인을 위해 같은 judgment_result 토픽에 재발행하는 방식은 사용하지 않는다.

log JSON은 `level`, `text`, `popup`으로 구성된다. ERROR 로그의 popup은 true다. 로그 수신으로 서비스 접수 성공이나 작업 완료를 임의 추정하지 않는다.

## 8. HMI 관리 서비스 타입 참고

다음은 공통 msg/srv에 있는 정의이며 **검사 측 서버 제공 목록이 아니다**. HMI 측 서비스로 구현한다면 경로·버전 충돌 정책·조회 JSON 구조는 별도로 확정해야 한다.

| 타입 | 요청 | 응답 |
|---|---|---|
| ListRecipes | 없음 | success, message, RecipeInfo[] recipes |
| GetRecipe | recipe_id, recipe_version(빈 값은 최신 저장 버전) | success, message, InspectionRecipe recipe |
| SaveRecipe | InspectionRecipe recipe | success, message |
| QueryResults | int64 run_id(0은 최근 실행), uint32 limit | success, message, string results_json |

RecipeInfo는 recipe_id, recipe_version, uint32 point_count다. SaveRecipe는 저장된 버전을 별도 반환하지 않으므로 새 버전 생성 방식도 HMI 관리 계약에서 정한다. `/cable_inspection/recipes/list`, `recipes/get`, `recipes/save`, `results/query` 같은 경로를 채택하더라도 검사 launch가 이를 생성한다고 가정하지 않는다.

## 9. 연동 검수 항목

다음은 **검수 절차이며 본 문서 작성 중 수행한 시험 결과가 아니다**.

| 시험 | 기대 결과 |
|---|---|
| 검사 PC 없이 HMI 관리 기능 기동 | 원본 목록·편집 가능, 검사 시작 불가 안내 |
| HMI를 Main보다 늦게 실행 | 보존 work_status 수신, SYNC로 생존 재확인 |
| 대기 중 3초 이상 유지 | 주기 SYNC 응답으로 Main 정상 표시 |
| 빈 ID/중복 Point/잘못된 조건 요청 | 해당 거절 code/message 표시, 실행 없음 |
| heartbeat 없이 유효 형식 요청 | HEARTBEAT_MISSING |
| 정상 요청 1회 | ACCEPTED, request_id/run_id 연결, snapshot과 후속 상태 수신 |
| 동일 ID·동일 레시피 재확인 | ALREADY_ACCEPTED, 같은 run_id, 추가 실행 없음 |
| 동일 ID·다른 레시피 | REQUEST_ID_CONFLICT |
| 응답 timeout | 접수 여부 미확정 표시, 새 ID 자동 요청 없음 |
| 실행 중 원본 레시피 수정 | 실행 snapshot/표시 기준 유지, 다음 실행만 새 버전 사용 |
| PAUSE/통신 복구 | PAUSED 확인 후 수동 RESUME; 자동 재개 없음 |
| 로봇상태만 또는 Main만 끊김 | 두 연결을 독립적으로 만료 표시 |
| 측정 null/valid=false/만료 | 0 대신 미확인 표시 |
| 수동 HOME | operation=HOME, request_id 빈 값, 새 검사 이력 생성 안 함 |
| 결과 저장·HMI 재접속 | 결과 중복 처리, 유실 가능 구간 표시, DB 조회 확인 |

유효 START/HOME/RESUME 시험은 실제 장비 동작을 발생시킬 수 있다. 비동작 검증과 장비 운전 시험을 구분해 실시한다. 검사 측 기존 비동작 통합 테스트는 `test/test_standalone_ros.py`이며 정상 START 실행을 검증하는 시험은 아니다.

## 11. 시퀀스 정합성 반영

Entry pose로의 접근은 MoveJ(allow_incomplete=True)이며, 목표 확인 시간 초과 시 감속 정지하고 미도달 결과를 기록한 뒤 후속 단계를 진행한다. Entry pose 이후 Soft Grip과 함께하는 진입은 Tool +Z 상대 직선 이동이다. Entry 최대거리 25 mm 검증은 유지하고, Pull 거리 및 Entry/Pull 시간은 레시피의 유한한 양수 값을 사용한다. PR #10에서 추가한 Pull 25 mm·시간 10 s 상한은 제거했다. 전체 포인트 순회 완료, pending_judgments 없음, 각 포인트 motion_status=SUCCESS, 유효한 PASS/FAIL/SYSTEM_ERROR 결과 및 log_saved=true가 완료 조건이다. adaptive_grip_status/pull_status/judgment_status는 별도 완료 게이트로 검사하지 않는다. SYSTEM_ERROR도 이 조건을 만족하면 Job 종료 및 최종 Home이 가능하다. 운영 정책 복원 범위는 [08 문서](08_PR09_운영정책_복원결과_2026-09-23.md)를 따른다. `gripper_busy`는 기록용이며 파지 완료나 Home 진입의 게이트로 사용하지 않는다. Hard Grip은 목표 폭 도달 또는 실측 폭 안정화로 완료를 판단한다.

검사측 외부 통신의 ROS 소유 노드는 ccc_hmi_node로 통합했다. 기존 토픽·서비스·QoS·필드는 동일하며 HMI 프로그램 변경은 필요하지 않다. 통합 테스트의 유효 START 사례는 Worker 시작을 대체하여 접수·중복 처리까지만 검증하며 실물 동작은 수행하지 않는다.

START는 Home 복귀를 요구하지 않고 장비 점검 후 Work Access 도달을 확보한다. 이미 Access이면 유지, 작업영역 내부이면 Safe Escape 후 Access, Home 등 작업영역 밖이면 Access로 이동한다. HMI 화면의 START 활성 조건에도 대기·정지·오류 상태와 work_active=false를 반영한다.
