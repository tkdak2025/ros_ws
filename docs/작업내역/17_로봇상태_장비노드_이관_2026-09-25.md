# 로봇 상태 수집의 장비 노드 이관

별도 `RobotStateNode`가 하던 상태 수집을 기존 Robot·GripperTool에 이관했다. `diagnostics/node_robot_state.py`, `robot_state_node` 실행 등록, launch 등록과 내부 중계 토픽을 제거했다. 판정 단독 디버그 실행과 수동 조회 도구는 유지한다.

## 책임과 실행

| 대상 | 책임 |
|---|---|
| `robot/m0609.py` | 로봇 조회 서비스 정의·클라이언트·응답 해석. 모션과 모니터링에서 기존 조회 클라이언트를 공유하고 요청 future는 별도로 관리 |
| `robot/node_robot.py` | 비동기 상태 조회, 채널별 미완료 요청 1건 제한, 수신 시각·오류·유효성 관리 |
| `gripper_tool/rg2.py` | 기존 RG2 구독에서 폭을 한 번 계산. 잘못된 피드백은 무효 처리 |
| `gripper_tool/node_gripper_tool.py` | 폭 피드백의 유효성·경과시간 제공 |
| `hmi/interface.py`, `hmi/node_hmi.py` | 장비 상태를 읽어 기존 외부 JSON·토픽·QoS로 발행 |
| `sequence/main/node_main.py` | 장비를 포함한 모든 노드의 콜백을 한 executor에서 처리. 모션은 기존 한 Worker에서 실행 |

장비 API는 내부에서 `spin_once()`를 호출하지 않는다. Worker에서 명령 요청 후 10 ms 간격으로 완료와 STOP을 확인한다. ROS 응답은 Main executor가 처리한다. 상태 조회 콜백은 응답을 기다리지 않으며 시퀀스의 STOP 감시를 호출하지 않는다. STOP 이후에도 상태 조회가 지속된다.

종료 시 새 작업을 받지 않고 STOP을 요청한다. Worker가 정지 처리하는 동안 executor를 계속 돌리고, Worker 종료 후 executor와 노드를 해제한다. 장비 API를 단독 디버깅하는 경우에도 호출 스레드와 별도로 해당 노드를 executor에서 처리해야 한다. 동일 executor의 콜백 안에서 동기 장비 API를 호출하면 안 된다.

## 유지한 외부 동작

- `/cable_inspection/robot_status`는 HmiNode가 발행한다. 필드·JSON 타입·QoS depth 10을 유지한다.
- 로봇 조회 기본 주기 0.2초, 활성 Tool/TCP 이름 1초, 요청 시간 제한 1초, 유효기간 2초.
- 상태 발행 타이머 0.1초. 실제 하드웨어에서의 주기·지연 상한을 보장하는 수치는 아니다.
- 미수신·오류·만료 측정값은 null이며 validity·age_s·errors를 제공한다.
- gripper busy는 참고값이며 파지나 상태 수집의 실행 제한에 사용하지 않는다.
- 기존 `internal/robot_status` 중계는 제거했다. 외부 HMI UI 코드는 수정하지 않았다.
- 이전 상태 노드의 독립 실행 명령과 ROS 파라미터는 제거했다. 위 기본값은 장비 코드에서 관리한다.

## 검증

기존 명령 순서·판정·START·HOME·STOP 회귀 검증을 유지했다. 다음 시험을 추가했다.

1. RG2 정상/NaN/만료/재수신에서 값과 유효성 전환, busy와 무관한 상태 제공.
2. 로봇 조회 미완료 중 중복 요청 방지와 STOP 상태에서의 조회 지속.
3. 격리 ROS 모의 서버에서 MoveJ 응답을 보류하고, 같은 시간에 실제 Robot·GripperTool 노드와 HmiNode의 상태 갱신을 확인.
4. 보류 중 Main 종료 요청 시 실제 STOP 서비스 응답·정지 확인·Worker 종료가 3초 안에 완료되는지 확인. 이후 상태 조회 지속도 확인.

검증 실행: ROS/설치 환경 적용 후 `python3 src/cable_inspection/cable_inspection/diagnostics/check_inspection.py --with-ros`.

실물 명령은 보내지 않았다. 실물 드라이버의 동시 조회 부하, 장시간 측정 주기와 STOP 지연은 현장 확인 대상으로 남는다.
