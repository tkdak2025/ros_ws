# 검사 PC ↔ 별도 HMI PC ROS 2 연동

기준: 2026-09-23 현재 cable_pkg 코드. HMI 코드는 수정하지 않았다.
이 문서는 구현된 통신 규격이며 두 PC 간 실제 통신 시험 완료를 의미하지 않는다.

## 1. 실행 구성

검사 PC: `sodreal`로 로봇/RG2를 실행하고 아래 명령으로 Main/Judgment만 실행한다.
기존 terminal 모드 시퀀스와 콘솔은 종료하고 전환한다.

```bash
cd /home/rokey/Desktop/ROKEY9/ROKEY_3/PRJT_CCCIS/ros_ws
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch cable_pkg sequence_bringup.launch.py control_mode:=hmi
```

HMI PC: 담당자의 HMI만 실행한다. 로봇 bringup/Main/Judgment는 검사 PC에만 둔다.
`system_bringup control_mode:=hmi`는 검사 PC에도 HMI를 실행하므로 이 분리 구성에서는 사용하지 않는다.
`robot_monitor_node`나 mock 노드를 같은 `/cable_inspection/status`의 발행자로 함께 실행하지 않는다.
Main이 운영 상태를 발행한다. 별도 실시간 센서 표시 연동은 현재 계약에 포함되지 않는다.

## 2. 두 PC 환경

검사 측 조회 환경은 ROS Jazzy, ROS_DOMAIN_ID=50, RMW_IMPLEMENTATION=rmw_fastrtps_cpp,
ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET이다. 실제 실행하는 두 터미널에서도 아래 값을 맞춘다.
양 PC가 서로 통신 가능한 같은 서브넷인지 확인한다. 별도 Discovery Server 구성이 있다면 양쪽 설정을 함께 확인한다.

```bash
source /opt/ros/jazzy/setup.bash
export ROS_DOMAIN_ID=50
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
unset ROS_LOCALHOST_ONLY
# 각 PC의 워크스페이스에서
source install/setup.bash
```

HMI PC에도 검사 PC와 동일한 `cable_interfaces` 패키지가 필요하다.
제공된 `cable_interfaces/` 디렉터리를 HMI 워크스페이스의 `src/`에 복사하고 빌드한다.

```bash
colcon build --packages-select cable_interfaces
source install/setup.bash
ros2 interface show cable_interfaces/msg/InspectionResult
```

## 3. 외부 토픽 계약

기본 namespace는 루트다. 아래 타입을 정확히 사용한다.

| 방향 | 토픽 | 타입 | 주기/용도 |
|---|---|---|---|
| HMI → 검사 | `/cable_inspection/command` | `std_msgs/msg/String` | JSON 명령, 버튼 동작 시 1회 |
| HMI → 검사 | `/cable_inspection/hmi_heartbeat` | `std_msgs/msg/Empty` | 0.5초마다 권장 |
| 검사 → HMI | `/cable_inspection/status` | `std_msgs/msg/String` | JSON 상태, 0.1초마다 |
| 검사 → HMI | `/cable_inspection/log` | `std_msgs/msg/String` | JSON 로그, 발생 시 |
| 검사 → HMI | `/cable_inspection/judgment_result` | `cable_interfaces/msg/InspectionResult` | Point별 판정/오류 갱신 |

QoS는 RELIABLE, VOLATILE, KEEP_LAST를 기준으로 연결한다. HMI 측 depth=50 사용 가능.
결과는 `(run_id, point_id)`로 갱신하며 중복 수신을 새 검사로 누적하지 않는다.
커스텀 메시지 전체 필드 정의는 첨부한 `InspectionResult.msg`가 기준이다.
`/cable_inspection/judgment_request`는 검사 PC 내부용이며 HMI에서 발행하지 않는다.

## 4. 명령과 버튼

`String.data`는 다음 JSON 문자열이다.

```json
{"name":"START","args":{"recipe_id":"rcp_BMW_LWR_01"}}
```

| HMI 기능 | name | args | 허용 조건 |
|---|---|---|---|
| 레시피 선택 | SELECT_RECIPE | recipe_id | SYSTEM_READY, 작업 없음 |
| 검사 시작 | START | recipe_id 선택 | SYSTEM_READY, 작업 없음 |
| 일시정지 | PAUSE | {} | RUNNING/PAUSE_REQUEST, 현재 동작 완료점에서 정지 |
| 이어하기 | RESUME | {} | PAUSED, Heartbeat 정상 |
| 작업 정지 | STOP | {} | 실행 중 정지 요청, 자동 Home 없음 |
| 원점복귀 | HOME_RETURN 또는 MOVE_HOME | {} | SYSTEM_READY/STOPPED/ERROR, 작업 없음 |
| 상태 동기화 | SYNC | {} | 현재 상태만 재발행 |

현재 `ESTOP`, `ESTOP_RESET`, `MOVE_TO_POINT`, `SET_SPEED`는 지원하지 않는다.
소프트웨어 작업 정지 버튼은 `STOP`을 전송한다. 이를 하드웨어 비상정지로 표시하지 않는다.
STOP 후에는 RESUME 대신 Home 성공 → SYSTEM_READY → 새 START 순서다.

레시피 기본값은 `rcp_BMW_LWR_01`, 실행 순서는 HARNESS_01 → HARNESS_02 → HARNESS_03.
HMI는 status.available_recipes에서 선택한다. 파일 경로나 레시피 편집 내용을 보내는 API는 없다.
원점복귀: 작업영역 안이면 Work Access를 거친 뒤 전체 관절 0도로 단일 MoveJ,
밖이면 바로 전체 관절 0도로 단일 MoveJ. 작업영역 Z 최솟값은 60 mm다.

## 5. 상태·판정 표시

- `run_state`: SYSTEM_READY / RUNNING / PAUSE_REQUEST / PAUSED / STOPPED / ERROR.
- `state`: SYSTEM_READY를 IDLE로 표현하는 호환 필드.
- `control_mode`: hmi여야 HMI 명령을 받는다. terminal이면 HMI 명령은 처리하지 않는다.
- `control_connected`: HMI Heartbeat 유효 여부.
- `selected_recipe_id`, `available_recipes`: 현재 선택 및 등록 목록.
- `run_id`: int64 실행 식별자. 결과와 동일한 값을 유지한다.
- `current_point`, `current_step`, `resume_point`, `execution_index`, `total_points`, `progress_percent`: 진행 정보.
- `pending_judgments`, `job_summary`: 판정 대기 및 검사 집계.
- `alarm`: 마지막 오류 문자열. 현재 동작 완료 여부는 run_state와 로그를 함께 확인한다.

진행률 100%와 JOB_COMPLETE 로그만으로 최종 Home 완료를 판정하지 않는다.
Home 중에도 RUNNING이며 단독 Home은 current_point가 비어 있을 수 있다.
현재 전용 최종 Job 완료 이벤트, 명령 request_id/ACK, 과거 결과 재전송은 없다.
SYNC는 결과 재조회가 아니다. HMI는 검사 시작 전 결과 구독을 준비한다.

결과 `result`는 PASS / FAIL / SYSTEM_ERROR다. SYSTEM_ERROR를 제품 FAIL로 합산하지 않는다.
`judgment_status`와 `sequence_status`는 판정/동작 처리 상태이며 제품 판정과 별개다.
폭 필드는 `soft_width_mm`, `pull_width_mm`, `width_delta_mm`, `grip_failure_width_mm`를 그대로 표시한다.
Soft 기준 폭을 Hard 직후 폭으로 이름만 바꾸어 매핑하지 않는다.
유효한 검사에서 Pull 최소 폭 16 mm 미만은 FAIL_GRIP_WIDTH다.
`task`, `joint`는 검사에 사용한 Entry 좌표이며 실시간 현재 위치가 아니다.
`db_saved`는 현재 false이며 HMI 저장 완료를 Main에 확인시키는 ACK는 없다.

## 6. Heartbeat와 통신 확인

현재 HMI Heartbeat 제한은 2초, 복구 대기 상한은 30초다.
유실 시 현재 동작 완료점에서 Pause, 복구 후 명시적 RESUME, 상한 만료 시 COMM_ERROR 종료.
HMI의 조작 불능을 별도 Heartbeat 프로세스로 가리지 않도록 실제 HMI 생존 주기에 연결한다.

HMI PC에서 아래를 각각 실행해 상태·토픽 타입을 먼저 확인한다. 로봇 이동 명령은 아니다.

```bash
ros2 topic info /cable_inspection/status --verbose
ros2 topic echo /cable_inspection/status std_msgs/msg/String --once
ros2 topic info /cable_inspection/judgment_result --verbose
ros2 topic pub --once /cable_inspection/command std_msgs/msg/String '{data: "{\"name\":\"SYNC\",\"args\":{}}"}'
```

검사 PC에서는 실제 HMI의 Heartbeat 수신을 확인한다.

```bash
ros2 topic hz /cable_inspection/hmi_heartbeat
```

연결 확인 후 HMI 버튼의 명령과 log/state 응답을 대조한다.
START/Home 버튼 실물 시험은 작업자가 수행한다. 이번 문서 작성 중 로봇 명령을 보내지 않았다.

## 7. 기존 cable_hmi와 다른 항목

현재 저장소의 HMI 코드를 참고하는 담당자는 특히 아래 차이를 반영해야 한다.

| 기존 HMI | 현재 검사 시퀀스 |
|---|---|
| ESTOP 전송 | STOP만 지원, 비상정지 해제 API 없음 |
| `/cable_inspection/result`, String JSON | `/cable_inspection/judgment_result`, InspectionResult |
| PASS/FAIL/INCOMPLETE 중심 분류 | SYSTEM_ERROR 별도 표시 필요 |
| Hard 기준 폭/폭 변화 필드 | Soft 기준 폭/Pull 최소 폭/부호 있는 차이 |
| 실시간 힘·TCP·속도 기대 | 현재 status에 해당 실측 필드 없음 |
| progress를 monitor가 status로 변환 | Main이 status 직접 발행, monitor와 동시 발행 금지 |

상세 필드 설명은 `HMI_인터페이스_수동제어.md`를 함께 참고한다.
