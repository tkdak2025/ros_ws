# HMI 로봇상태 / 작업상태 분리 인터페이스

> **노드 구조 및 시작 인터페이스 개편:** 현재 HMI 레시피 관리/전체 레시피 START 서비스/결과 저장은 [노드 구조 가이드](../01_commons/CCCIS_노드구조_개편_2026-09-23.md)를 우선 적용합니다.

기준: 2026-09-23. 검사 PC `cable_inspection` 구현 기준.
이 문서는 기존 단일 `/cable_inspection/status` 계약의 상태 부분을 대체한다.
HMI PC의 화면 코드는 별도 담당자가 아래 계약으로 변경해야 한다.
명령, HMI Heartbeat, 로그, InspectionResult 인터페이스는 변경하지 않는다.

## 1. 토픽과 책임

| 토픽 | 발행 노드 | 타입 | 발행 정책 | QoS |
|---|---|---|---|---|
| `/cable_inspection/robot_status` | `ccc_hmi_node` | `std_msgs/msg/String` JSON | 상시 10 Hz, 서비스 수집 기본 5 Hz | RELIABLE / VOLATILE / depth 10 |
| `/cable_inspection/work_status` | `ccc_hmi_node` | `std_msgs/msg/String` JSON | 작업 중 10 Hz, 대기 중 변경/SYNC 시 | RELIABLE / TRANSIENT_LOCAL / depth 1 |

- Main은 기존 `/cable_inspection/status`를 더 이상 발행하지 않는다.
- 로봇상태에는 실시간 장비 값, 작업상태에는 실행 상태·진행·검사 조건·Pull 측정값을 둔다.
- 작업 중은 Worker 실행 중 또는 RUNNING / PAUSE_REQUEST / PAUSED다. 초기화·단독 Home·정지 처리도 포함한다.
- 준비/종료/오류/레시피 선택/제어 연결 변경은 작업이 없어도 발행한다. 완전 무발행이면 HMI가 시작 가능 여부와 종료를 알 수 없기 때문이다.
- work_status 구독자는 TRANSIENT_LOCAL을 사용하면 늦게 접속해도 최종 상태를 받는다. VOLATILE 구독자는 SYNC로 현재 상태를 요청한다.
- 대기 중 work_status가 안 오는 것 자체는 통신 오류가 아니다. 최신 Main 생존 확인이 필요하면 SYNC를 요청한다. 로봇상태 수신만으로 Main 생존을 판단하지 않는다.
- 터미널 콘솔은 work_status를 구독하고 1초마다 SYNC를 요청해 기존 최신 상태 검사를 유지한다.

## 2. 로봇상태

전용 노드는 읽기 서비스와 RG2 피드백만 사용한다. 이동·정지·Tool/TCP 설정·그리퍼 명령을 보내지 않는다.
Main의 장비 노드와 별개의 ROS 노드/클라이언트를 사용하며 서비스 응답을 기다리는 동안 executor를 막지 않는다.
채널별 미완료 요청은 최대 한 건이다. 기본 응답 제한 1초, 데이터 만료 2초다.

| 필드 | 의미 |
|---|---|
| `schema_version`, `stamp` | 스키마 버전 1, 발행 시각(ISO 8601) |
| `robot_connected` | 최근 유효한 로봇 상태 조회 응답 존재. 운전 가능 판정과 다름 |
| `gripper_connected` | 최근 유효한 RG2 폭 피드백 존재. 명령 서비스 가용성 판정과 다름 |
| `task`, `joint` | 현재 TCP(BASE mm/deg)와 관절각(deg), 각 6개 또는 null |
| `wrench_base` | BASE 힘/모멘트 6축, N/Nm 또는 null |
| `force_norm_n` | 원시 힘 XYZ 크기. Pull 정지 기준 힘이 아님 |
| `gripper_width_mm` | RG2 실측 폭(mm) 또는 null |
| `robot_state_code`, `motion_status` | GetRobotState / CheckMotion 원시 코드 또는 null |
| `robot_motion` | CheckMotion이 이동 중이면 MOVING, 정지면 로봇 상태명, 판단 불가면 빈 문자열 |
| `servo`, `servo_source` | 상태 코드 기반 ON/OFF 추정, 미확인이면 빈 문자열. source는 robot_state_inference |
| `tool.name`, `tool.tcp` | 활성 Tool/TCP 조회 이름 또는 null (기본 1초마다 조회) |
| `validity` | 채널별 유효 여부 |
| `age_s` | 채널별 수신/오류 기록 이후 경과 초. 아직 기록 없으면 null |
| `errors` | 미수신·조회 실패·만료 채널의 사유 |

모든 채널이 동시에 측정된 스냅샷은 아니다. 각 age_s와 validity를 확인한다.
조회 실패/만료 값은 null이다. 0으로 치환하거나 오래된 값을 현재값처럼 표시하지 않는다.
HMI는 robot_status 자체가 끊기면 자체 수신 시간으로 장비 표시를 만료시켜야 한다.
Tool 무게·Force Zero 완료·전체 속도 %는 이번 인터페이스에서 제공하지 않는다.

## 3. 작업상태

기존 작업 필드는 유지한다:
`state`, `run_state`, `alarm`, `control_mode`, `control_connected`, `available_recipes`,
`run_id`, `recipe_id`, `selected_recipe_id`, `job_id`, `recipe_version`, `execution_index`,
`resume_point`, `total_points`, `current_point`, `current_step`, `pending_judgments`,
`progress_percent`, `job_summary`.

추가 필드:

- `schema_version`: 1.
- `stamp`: 이번 발행 시각. 보존된 메시지는 과거 발행 시각을 유지한다.
- `work_active`: Worker 또는 작업 상태가 활성인지 여부.
- `criteria`: 현재 Point의 실행 스냅샷에서 추출. Point가 없으면 `{}`.
- `measurement`: 현재 Point와 일치하는 최근 검사 측정값. 없으면 null.

```json
{
  "criteria": {
    "required_pull_force_n": 15.0,
    "max_displacement_mm": 5.0,
    "pull_max_distance_mm": 25.0,
    "grip_width_mm": 21.0
  },
  "measurement": {
    "sample_stamp": "2026-09-23T16:00:00.000+09:00",
    "age_s": 0.1,
    "valid": true,
    "phase": "PULL",
    "measurement_kind": "PULL",
    "pull_force_n": 11.2,
    "pull_displacement_mm": 2.1
  }
}
```

Pull 외 구간에서는 pull_force_n/pull_displacement_mm이 null일 수 있다.
measurement_kind/phase는 측정 당시 값이다. 다른 동작으로 넘어갔을 때 과거 Pull 값을 현재 동작으로 해석하지 않는다.
2초보다 오래된 샘플은 valid=false다. 최종 최대 힘/판정은 judgment_result로 확인한다.
측정 캐시는 시작/Home 및 Point 설정 때 초기화한다. status 발행에서는 sample()이나 장비 서비스를 호출하지 않는다.
진행률 100%가 최종 Home 완료를 뜻하지 않는다. work_active와 run_state를 함께 확인한다.

## 4. HMI 변경 범위

1. 기존 status 구독을 robot_status와 work_status 두 개로 분리한다.
2. 로봇 패널은 robot_status만으로 갱신한다. 작업상태가 없을 때에도 유지한다.
3. 진행/조건/Pull 게이지는 work_status로 갱신한다. 새 메시지로 객체를 통째로 교체해 다른 패널 값을 지우지 않는다.
4. 대기 중 작업값은 비우거나 마지막 작업 결과로 구분해 표시한다. 최종 결과 이력은 judgment_result를 사용한다.
5. null, validity=false, measurement.valid=false는 미확인/만료로 표시한다. 0.0으로 표시하지 않는다.
6. 작업 기록 노드도 work_status를 구독한다. 기존 status timeout을 그대로 적용하지 않는다.
7. 작업 제어 버튼 활성은 Main의 상태·응답으로 결정한다. robot_connected는 운전 승인 신호가 아니다.

기존 저장소 cable_hmi/mock/robot_monitor_node는 별도 기존 계약이다. 이번 변경은 검사 PC와 터미널 콘솔에 적용했다.
기존 HMI와 통합 launch를 그대로 사용하면 새 상태를 표시하지 못하므로 HMI 담당자의 구독 변경 후 연동한다.

## 5. 실행과 확인

```bash
# ros_ws에서 ROS 및 두산 underlay 적용 후
colcon build --symlink-install --packages-select cable_inspection
source install/setup.bash
ros2 launch cable_inspection inspection.launch.py control_mode:=hmi
```

inspection.launch.py는 Main 내부에서 장비·판정·HMI 노드를 함께 실행한다. 로봇 상태는 RobotNode가 비동기로 조회하고 그리퍼 상태는 기존 RG2 구독으로 수집한다. 별도 상태 노드는 실행하지 않는다.

확인 명령은 로봇 이동을 요청하지 않는다.

```bash
ros2 topic echo /cable_inspection/robot_status std_msgs/msg/String --once
ros2 topic echo /cable_inspection/work_status std_msgs/msg/String --qos-durability transient_local --once
```

상태 조회 기본 주기 0.2초(Tool/TCP 이름은 1초), 응답 제한 1초, 유효기간 2초, HMI 발행 주기 0.1초다. 이 값은 현재 장비 노드 설정값이며 제거한 상태 노드의 ROS 파라미터는 더 이상 사용하지 않는다. RG2 피드백은 real/virtual 모드별 기존 장비 구독을 사용한다.

## 6. 검증과 남은 현장 확인

- 상태 만료·조회 타임아웃·작업 중 주기 발행·대기 무주기·최종 상태·Point 일치 검사를 포함한 단위/회귀 테스트 35개 통과.
- 격리된 Domain 232, /status_test 모의 서비스에서 실제 ROS 통신 확인:
  비동기 좌표/힘 조회, 이동 상태, RG2 피드백 만료, 늦은 work_status 구독, 대기 무주기 확인.
- 실물 로봇 이동/정지 명령은 보내지 않았다.
- 실제 두 PC에서 변경된 HMI 표시, 실물 서비스 조회 부하와 검사 샘플 주기 영향은 현장 검증이 필요하다.

검사측 HMI 전담 노드 적용 후 외부 상태 발행자는 ccc_hmi_node로 통합했다. 로봇상태 수집은 ccc_robot_node, 그리퍼 피드백은 ccc_gripper_tool_node가 담당하며 HmiNode가 각 장비의 상태 API를 읽는다. 기존 외부 토픽·JSON·QoS는 동일하다.
