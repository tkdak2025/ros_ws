# 04. 시퀀스 설계·구현 대조 및 보류 체크

- 작성일: 2026-09-23
- 비교 기준: `CCCIS_Sequence_Documents_2026-09-22`의 #00~#07, Common #01 및 `sequence_contracts.yaml`
- 구현 기준: `ef82ae7`의 `cable_inspection` 및 이번 수정
- 범위: 검사·로봇 제어만. HMI 코드는 변경하지 않음.
- 원칙: 후속 대화/작업 기록에서 바뀐 정책은 옛 설계로 자동 복원하지 않고 보류한다. 과거 대화 원문을 모두 확인한 것은 아니므로, 기록된 변경 사실과 사용자 합의 여부를 구분한다.

## 2. 시퀀스별 대조 결과

| 설계 | 확인된 구현 | 판정 |
|---|---|---|
| #00 Main | 한 Job, 활성 Point 순서, snapshot 복사, Initialize→Home→Access→Point loop→Access→Finish→Home, STOP 후 자동 Home 없음 | 큰 흐름 일치. F02/F03/F05 수정. 시작 방식·노드 분리는 H01 유지 |
| #01 Initialize | Robot/HMI/System/Inspection/활성 포인트와 Robot 재확인, 초기화 실패 시 모션 진입 없음 | 기본 흐름 일치. F02/F03 수정. 입력 좌표/방향 정책은 H03/H04 |
| #02 Home Return | 내부: Access→전체 관절 0도 Home, 외부: 바로 Home; Relax/Escape 미호출 | **설계 불일치 유지·보류 H02**. 허용오차 파라미터화도 H02에서 함께 검토 |
| #03 Point Transition | Open→Ready MoveJ→Entry MoveJ(allow_incomplete=True); 다음 Point에서 공통 Access를 매번 경유하지 않음 | 이동 종류·Entry 도달 조건은 **보류 H03** |
| #04 Adaptive Grip | Soft→추가 진입→Soft 종료 실측 폭→Hard 완료 확인. Entry ABC로 방향 결정 | 폭 기준·방향·조건은 **보류 H04/H05** |
| #05 Pull | 반대 방향 직선 이동, 힘/거리/시간 종료, 감속 구간 측정 포함, 비동기 판정 후 Open→Entry→Ready | 주요 흐름 일치. F04 수정. 숫자 조건은 **보류 H05** |
| #06 Judgment | Queue/Worker, PASS/FAIL/SYSTEM_ERROR, Pull 최소 폭 16 mm 미만 FAIL_GRIP_WIDTH, 결과·사유 발행 | 비동기 구조 일치. 결과 분류·폭 정책은 **보류 H04/H06** |
| #07 Finish | Access에서 결과·로그·통신 확인, 대기 만료 시 Pause 후 재확인, 성공 후 Home | F01/F03/F05 수정. SYSTEM_ERROR 정상 종료 허용은 **보류 H06** |
| Common #01 | 완료점 Pause, Context 유지, heartbeat 복구 후 명시적 RESUME, 통신복구 제한시간 초과 종료 | 기본 흐름 일치. 장비별 실제 정지 지점·시간은 실물 검증 필요 |

이 표는 소스·설계 및 오프라인 테스트 범위의 대조이며, 충돌 없는 로봇 경로나 실물 안전 성능을 증명하지 않는다.

## 3. 변경 기록이 있어 보류한 체크항목

### H01 — 시작 인터페이스와 노드 분리

- [ ] 옛 START 토픽/Recipe ID 방식으로 되돌리지 않고 현재 StartInspection 전체 레시피 서비스, request_id, snapshot, robot_status/work_status 분리를 설계 개정본에 반영한다.
- 근거: 현재 대화에서 노드 구조 개편 완료 및 검사/HMI 책임 분리를 명시했고 `ef82ae7`과 README에 반영됨.
- 이번 처리: 현 계약 유지. `cable_hmi`, 공통 msg/srv 구조 변경 없음.

### H02 — Home Return 경로, Grip Relaxation / Safe Escape

- [ ] **내부 Relax→Escape→Access→Safe Home Route를 복원할지**, 후속 Access→0도 Home 정책을 유지할지 확정한다.
- [ ] 복원한다면 Tool 접근축, 탈출 상한, 이완 폭/힘, 검증된 Home 경유 경로를 확정한다. 좌표나 축을 임의로 입력하지 않는다.
- [ ] 현재 Work Access는 work_area 내부에 있다. 큰 작업영역에서 30 mm 이내 탈출이 가능한지와 Home 호출 시점을 검토한다.
- [ ] Home 도달 tolerance(현재 관절 0도 ±0.1도 고정)를 시스템 파라미터로 만들지 확정한다.
- 근거: `82c81e8`이 기존 Relax/Escape 호출을 삭제하고 Access→단일 0도 MoveJ로 바꿈. 같은 커밋에서 safe_home_route/allowed_workspace 제거, tool_approach_axis 선택화, 대응 테스트 변경. `HMI_ROS2_연동_2026-09-23.md` 4절에도 변경 경로가 명시됨.
- 합의 증거 한계: 명시적 후속 구현·인계 기록은 있지만, 이 세션에 이전 대화 원문은 없어 사용자가 직접 요청했는지는 단정하지 않는다.
- 이번 처리: **모션 경로를 복원하지 않고 보류**. 현재 tool_approach_axis=null이며 Escape를 연결하면 운영 설정과 충돌한다. safe_escape 함수가 존재한다는 이유만으로 이미 실행된다고 보지 않는다.

### H03 — Entry 접근 종류와 도달 미완료 처리

- [ ] 설계의 Ready→Entry MoveL/도달 확인으로 복원할지, 현재 교시 joint 기반 MoveJ를 유지할지 확정한다.
- [ ] Entry `allow_incomplete=True`로 도달 미확인 시에도 다음 단계로 진행하는 정책을 유지할지 확정한다.
- 근거: 패키지 README의 09-23 피드백은 Ready/Entry MoveJ 및 task/joint 동시 교시를 명시. `시퀀스 작업내역.md` C05는 Entry 도달 여부 기록·진행을 명시하고 기존 테스트도 이를 고정함.
- 이번 처리: 이동 방식과 미도달 정책 변경 보류. 실물 도달 검증 완료로 해석하지 않는다.

### H04 — 방향·Grip 폭 기준·판정 종류

- [ ] 설계의 별도 entry_direction 대신 Entry ABC의 Tool +Z를 사용하는 현재 방향 계약을 설계에 반영할지 확인한다.
- [ ] Hard 직후 폭/폭 변화 Slip 대신 Soft 종료 기준 폭과 Pull 최소 폭 16 mm 기준을 유지할지 확인한다.
- [ ] MISSING을 복원하지 않고 FAIL_GRIP_WIDTH/SYSTEM_ERROR를 쓰는 후속 판정 규칙을 설계에 반영한다.
- 근거: `시퀀스 작업내역.md`는 “현재 대화의 판정 규칙으로 대체”되었다고 명시. `7941f22`, `a86b281`, 현재 README와 결과 메시지도 후속 정책을 사용함.
- 이번 처리: 현재 방향·판정 규칙 유지. old MISSING을 자동 복원하지 않음.

### H05 — 레시피 수치의 상충

- [ ] LAN 기준 힘은 #05/#06 본문 20 N, sequence_contracts.yaml 및 현재 LAN 예제 15 N 중 운영 기준을 확정한다.
- [ ] Entry 거리/Timeout/Force Guard, Pull 거리/Timeout/속도를 고정 제한으로 둘지 현재 포인트별 레시피 값으로 둘지 확정한다.
- 근거: 동일 설계 묶음 안에서도 수치가 다르고 Pull 속도는 TBD. 작업 기록에는 15 N 시험 및 감속 중 최대힘 집계 보완이 존재함.
- 이번 처리: 운영 레시피·좌표·힘·속도를 변경하지 않음. 문서 후보 수치를 임의로 장비에 적용하지 않음.

### H06 — SYSTEM_ERROR와 Job 정상완료

- [ ] 제품 결과와 별개로 judgment_status=ERROR 또는 sequence_status=INCOMPLETE인 Point가 있으면 #07에서 무조건 종료 보류할지 확정한다.
- 근거: #06/#07 설계는 ERROR/INCOMPLETE 정상완료 금지. 반면 후속 작업 기록은 SYSTEM_ERROR 결과와 Home 가능 여부를 분리하며 `test_07_three_results_can_complete_job`은 SYSTEM_ERROR를 포함해 완료 가능하도록 고정함.
- 이번 처리: **SYSTEM_ERROR 종료 정책 자체는 보류**. F01은 판정 PENDING 및 결과/판정 상태 불일치만 차단하며 기존 SYSTEM_ERROR+ERROR 완료 허용은 유지함.
