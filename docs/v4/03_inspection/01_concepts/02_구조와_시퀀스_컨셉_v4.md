# Concept 02 — 책임 구조와 시퀀스

버전: v4 · 기준일: 2026-09-25 · 범위: 검사파트와 HMI 통신 계약

[v4 문서 안내](../../00_문서안내_v4.md) · [변경 근거·확인 항목](../../01_commons/02_변경추적_및_확인항목_v4.md)

## 큰 구조

| 영역 | component / raw | 실행·통신 책임 |
|---|---|---|
| Robot | robot/m0609.py | robot/node_robot.py가 API·상태 수집 제공 |
| GripperTool | gripper_tool/rg2.py | gripper_tool/node_gripper_tool.py가 API·피드백 제공 |
| Recipe | recipe/recipe.py | recipe/node_recipe.py가 ROS 데이터 변환과 Recipe API 제공 |
| Sequence | seq_main / seq_inspection / seq_home_return | node_main.py가 구성과 단일 모션 Worker 실행 |
| HMI | hmi/interface.py | hmi/node_hmi.py가 외부 요청·상태·결과 통신 |

Robot과 GripperTool은 독립 장비 영역이다. raw 클래스와 API 클래스의 상속 구조는 장비 영역 안에 둔다. 시퀀스는 명령 API를 사용하여 단계 순서를 표현한다. 각 시퀀스가 다시 연결 객체를 만들지 않는다.

## 시퀀스 묶음

- Main: #00 전체 실행, #01 준비, #07 완료, 공통 Pause/Resume/STOP.
- Inspection: #03 접근, #04 파지/진입, #05 Pull/복귀; #06 판정은 별도 Worker.
- Home Return: #02 독립 component. Main 실행권 아래 호출하며 별도 모션 실행 노드를 추가하지 않는다.
- Recipe: 검사 동작을 실행하지 않고 다음 포인트·순회 현황·실행 결과를 관리한다.

`node_main`은 구성과 실행 수명, `seq_main`은 작업 정책을 담당한다. `motion`에는 공통 이동·계측·도달 확인을 두고 검사별 단계 순서나 판정은 두지 않는다. 데이터 구조는 해당 책임의 `data_models`에 두며 같은 레시피를 OperatingRecipe 같은 별도 구조로 복제하지 않는다.

## 실행과 비동기성

한 Main 프로세스에서 ccc_sequence_node, ccc_hmi_node, ccc_recipe_node, ccc_inspection_node, ccc_robot_node, ccc_gripper_tool_node를 구성한다. 5개 책임 영역이 반드시 5개 별도 프로세스를 뜻하지 않는다. 내부 component 호출은 Python API이며 모든 내부 호출을 ROS 왕복으로 바꾸지 않는다.

ROS executor는 서비스 응답·구독·타이머를 처리한다. 모션은 Main Worker 한 개, 판정은 Queue Worker에서 실행한다. Home과 Inspection의 동시 모션을 허용하지 않는다. 종료 시 Main은 STOP을 요청하고 Worker 정리가 끝날 때까지 필요한 executor 처리를 유지한다.

Robot 상태는 RobotNode의 비동기 요청으로, RG2 상태는 기존 구독 피드백으로 수집한다. HmiNode가 합쳐 외부로 송신한다. 독립 RobotState 노드를 재기동하거나 중복 상태 발행자를 추가하지 않는다.

## 의존성 확인 기준

실행 노드가 component를 조합하고, component가 필요한 API를 주입받는다. Recipe는 순회/결과용 데이터 구조를 참조하지만 시퀀스 실행을 호출하지 않는다. 인터페이스 변경 시 imports와 launch/setup 진입점을 함께 확인한다. 이 문서는 전 파일의 미래 순환참조 부재를 보증하는 분석 결과는 아니다.
